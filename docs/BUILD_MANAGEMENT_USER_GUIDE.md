# Active Build Management — User's Guide

**Audience:** maintainers and contributors of any `ruralpeds/*` repo using the build-management scaffold.
**Source repo:** [`ruralpeds/.github`](https://github.com/ruralpeds/.github) — `templates/build-management/`
**Last updated:** 2026-05-06

---

## 1. What this system does

Every repo gets a single, always-current document — **`BUILD.md`** — that
answers two questions at a glance:

1. What has been built?
2. What still needs to be built?

You do not edit `BUILD.md`. You edit `.build/manifest.yaml`. CI keeps the two
in sync, and signals from your CI workflow flip features from `building` to
`built` automatically when their PR passes tests.

When you want to plan new work, you **order a gap analysis** from the Actions
tab. That opens a PR proposing new features and gaps. Merging the PR is the
approval step — `BUILD.md` updates itself.

---

## 2. The four files you'll see

| File | Edit by hand? | Purpose |
|---|---|---|
| `BUILD.md` | **No** — auto-generated | The human view. Read-only. |
| `.build/manifest.yaml` | **Yes** — humans add features, automation flips status | Source of truth. |
| `.build/schema.json` | No (template) | Validates the manifest in CI. |
| `.gap-analysis/GAP_ANALYSIS.md` | Yes | Remediation backlog (separate from features). |
| `.gap-analysis/build-ledger.jsonl` | **No** — append-only by automation | Audit log of every status change. |

## 3. Installing into a new repo

From the consumer repo's root, on a feature branch:

```bash
curl -fsSL https://raw.githubusercontent.com/ruralpeds/.github/main/scripts/install-build-management.sh | bash
git add .build BUILD.md .github/workflows .gap-analysis/build-ledger.jsonl
git commit -m "chore: bootstrap build-management"
git push
```

Then open a PR. The first push of `BUILD.md` is committed by you; every push
afterwards will be regenerated by `build-md-render.yml`.

The installer is idempotent: re-running it skips any file that already exists.
Pass `--force` to overwrite.

## 4. Day-to-day workflows

### 4.1 Add a planned feature

1. Edit `.build/manifest.yaml`, append a new entry:

   ```yaml
   - id: FEAT-042
     name: FHIR Patient $everything endpoint
     description: Implement Bulk Data $everything export per FHIR R4.
     status: planned
     priority: P2
     owner: yourhandle
     gap_ref: null
     pr: null
     branch: null
     built_at: null
     acceptance:
       - Returns NDJSON with at least Patient + Observation + Encounter
       - Authenticated via SMART backend services
   ```

2. Open a PR. CI validates the manifest against the schema and regenerates
   `BUILD.md`. The PR fails if `BUILD.md` and the manifest are out of sync.

3. Merge. The feature shows up in `BUILD.md` as `💭 planned`.

> **Picking a `FEAT-NNN`:** use the next unused 3-digit integer. CI will fail
> a duplicate.

### 4.2 Start building a feature

Open a branch named `feat/FEAT-042-anything` (the `FEAT-NNN` token is what the
caller workflow looks for). Open a PR. The status flips:

- `approved` → `building` when CI starts
- `building` → `built` when CI succeeds and the PR is merged
- `building` → `approved` (rolled back) if CI fails

You don't edit the manifest for these transitions; the
`reusable-build-manifest.yml` workflow does it.

### 4.3 Mark a feature blocked

Edit the manifest by hand, set `status: blocked`, and reference the blocker:

```yaml
status: blocked
gap_ref: GAP-017
```

Commit, open a PR, merge. `BUILD.md` will show `⛔ blocked` with a link.

### 4.4 Order a gap analysis

When you want fresh proposals against the roadmap (e.g. quarterly planning):

**Option A — Actions tab:**
1. Go to **Actions → Gap Analysis — Order → Run workflow**.
2. Fill in `scope` (e.g. `Q3 FHIR ingestion roadmap`).
3. (Optional) Override `roadmap_paths` if your roadmap docs aren't named like the defaults.
4. (Optional) Add reviewers.

**Option B — issue comment:**

Comment `/gap-analysis` on any issue. The issue title becomes the scope.

Either way, a PR appears within ~2 minutes containing:

- New `GAP-NNN` entries appended to `.gap-analysis/GAP_ANALYSIS.md`
- New `FEAT-NNN` entries (status: `planned`) appended to `.build/manifest.yaml`

**Approval = merging the PR.** Edit any proposed entry first if you want to
adjust priorities, owners, or wording. After merge, `build-md-render.yml`
regenerates `BUILD.md` automatically.

## 5. Reading `BUILD.md`

```markdown
| Status | Count |
|---|---:|
| Built       |  12 |
| Building    |   3 |
| Approved    |   5 |
| Planned     |  18 |
| Blocked     |   2 |
| Total       |  40 |
```

The feature table sorts by:

1. `building` first (in flight)
2. `blocked` (needs attention)
3. `approved` (ready to start)
4. `planned` (backlog)
5. `built` (done — also listed in the History section by `built_at` desc)

Status emojis: 🔨 building · ⛔ blocked · 📋 approved · 💭 planned · ✅ built.

## 6. CI integration: how `built` actually gets stamped

The per-repo caller workflow (`build-manifest-caller.yml` from the template)
listens for two events:

| Event | Signal sent to manifest |
|---|---|
| `pull_request` opened/synced on a `feat/FEAT-NNN-*` branch | `started` → status `building` |
| `workflow_run` of your primary CI completes successfully | `passed` → status `built`, `built_at` set |
| `workflow_run` completes with failure/cancel/timeout | `failed` → status reverted to `approved` |

**Configuration you must do** in the caller workflow:

```yaml
on:
  workflow_run:
    workflows: ["CI"]   # ← rename to your repo's primary CI workflow name
```

Without that rename, `built` will never get stamped automatically. You can
still flip status by editing the manifest by hand, but you lose the automation.

## 7. Failure modes & how to recover

| Symptom | Cause | Fix |
|---|---|---|
| PR fails with "BUILD.md is out of sync" | You edited `BUILD.md` by hand, or your manifest change wasn't rendered | Run `python scripts/render_build_md.py --manifest .build/manifest.yaml --template templates/build-management/BUILD.template.md --out BUILD.md` locally and commit |
| PR fails with `manifest validation` | Schema violation (bad `status` value, missing `id`, duplicate `FEAT-NNN`) | Read the workflow log; fix the offending entry |
| Feature stays `building` after CI passes | Caller workflow's `workflows: ["CI"]` doesn't match your CI workflow name | Edit `.github/workflows/build-manifest-caller.yml` |
| `gap-analysis-request` PR is empty | All roadmap headings already overlap with existing features (overlap ≥ 0.5) | Use a more specific `scope`, or expand `roadmap_paths` |
| Ledger entries duplicated | Same CI run signalled twice (rare; webhook retry) | Harmless — ledger is append-only by design; downstream readers de-dup by `(feature, ts)` |

## 8. Gap analysis vs. build manifest — when to use which

| You want to track... | Use |
|---|---|
| A feature you plan to ship | `.build/manifest.yaml` |
| A bug, refactor, or compliance task with no shippable feature | `.gap-analysis/GAP_ANALYSIS.md` |
| A feature that is blocked by a gap | Both — feature in manifest with `gap_ref: GAP-NNN` |

The two systems are deliberately separate. Manifests answer *"what does this
repo do?"*; gaps answer *"what's wrong or missing?"*.

## 10. Quick command cheatsheet

```bash
# Bootstrap a new repo
curl -fsSL https://raw.githubusercontent.com/ruralpeds/.github/main/scripts/install-build-management.sh | bash

# Render BUILD.md locally (after editing the manifest)
python scripts/render_build_md.py \
  --manifest .build/manifest.yaml \
  --template templates/build-management/BUILD.template.md \
  --out BUILD.md

# Validate the manifest locally
python -c "import json, jsonschema; from ruamel.yaml import YAML; \
  jsonschema.validate(YAML(typ='safe').load(open('.build/manifest.yaml')), \
                      json.load(open('.build/schema.json')))"

# Propose a gap analysis locally (dry run; normally use the workflow)
python scripts/propose_gap_analysis.py \
  --scope "Q3 planning" \
  --roadmap-paths "ENTERPRISE_ROADMAP.md,YEAR_2_ROADMAP.md" \
  --manifest .build/manifest.yaml \
  --gap-doc .gap-analysis/GAP_ANALYSIS.md
```
