## Cryptographic Foundations

### 1.1 Algorithms & Standards

**Signing Algorithm: ECDSA (Elliptic Curve Digital Signature Algorithm)**

- **Curve:** NIST P-256 (secp256r1) — 256-bit security level
- **Hash function:** SHA-256 (FIPS 180-4)
- **Key size:** 256 bits (private) → 512 bits (public: 2× 256-bit coordinates)
- **Signature size:** 64 bytes (r || s, each 256 bits)

**Why ECDSA?**
- NIST-approved (FIPS 186-4)
- Smaller keys than RSA (256-bit = ~3072-bit RSA security)
- Faster signing/verification than RSA
- Suitable for high-volume auditing (1000+ signatures/day)

**Key Management: Keyless Signing via Sigstore Cosign**

Traditional PKI problems:
- Private keys stolen → attacker can forge signatures
- Key rotation → revocation, distribution complexity
- Escrow/backup → centralized trust

Cosign solution:
- **No private key on CI runner** — OIDC token used instead
- **Ephemeral certificate** — generated by Fulcio CA, valid <5 minutes
- **Short-lived** — reduces key exposure window to seconds
- **Audit trail** — certificate issuance logged via OIDC provider (GitHub)

**Flow:**
```
GitHub CI Job (e.g., release.yml)
  ↓
[Step: Generate signature]
  ├─ Create OIDC token (signed by GitHub)
  │  ├─ iss: "https://token.actions.githubusercontent.com"
  │  ├─ sub: "repo:ruralpeds/app:environment:production"
  │  ├─ aud: "sigstore"
  │  └─ exp: now() + 5 min
  │
  ├─ Exchange token with Fulcio CA
  │  ├─ Fulcio verifies OIDC signature (GitHub public key)
  │  ├─ Fulcio issues short-lived cert
  │  │  ├─ Subject: sigstore-signer
  │  │  ├─ Extensions: GitHub token claims (repo, branch, run ID)
  │  │  ├─ Validity: 5 min
  │  │  └─ Signed by Fulcio root CA
  │  └─ Fulcio returns cert + private key (in-memory only, never persisted)
  │
  ├─ Sign document hash
  │  ├─ Hash document with SHA-256
  │  ├─ Sign hash with ECDSA (using Fulcio-issued private key)
  │  └─ Signature = ECDSA(sha256_hash, private_key)
  │
  ├─ Discard private key (garbage collected)
  │
  └─ Return signature + certificate
      ├─ Signature (64 bytes)
      └─ Certificate (X.509, with GitHub token claims)

Private Key Never Persists:
  ├─ Not stored on runner
  ├─ Not stored in vault
  ├─ Not in git history
  ├─ Deleted after signature created (VM destroyed after job)
  └─ → Even if VM compromised, no key to steal
```

### 1.2 Hash Functions

**SHA-256 (FIPS 180-4)**

- **Output:** 256 bits (32 bytes)
- **Preimage resistance:** 2^256 operations required to find input
- **Collision resistance:** 2^128 operations required to find two inputs with same hash
- **Speed:** ~1 GB/sec on modern CPUs
- **Used for:** Every audit log entry, envelope, artifact

**Example audit log entry hash:**

```json
{
  "timestamp": "2026-05-02T15:30:45Z",
  "event_type": "release.created",
  "actor": "system/ci",
  "resource": "app@v2.3.1",
  "result": "success"
}

SHA-256(json_canonical_form) = 
  "abc123def456789abc123def456789abc123def456789abc123def456789abc1"
```

**Canonical JSON Form:**
```
Serialize without whitespace, keys in alphabetical order:
{"actor":"system/ci","event_type":"release.created","resource":"app@v2.3.1","result":"success","timestamp":"2026-05-02T15:30:45Z"}
```

## Hash Chain Architecture

### 2.1 Immutable Ledger Design

**Problem:** Single log entry can be modified without detection

**Solution:** Hash chain — each entry references previous entry's hash

**Structure:**

```json
Entry 1:
{
  "id": 1,
  "timestamp": "2026-05-02T15:00:00Z",
  "event_type": "release.created",
  "hash": "sha256:abc123...",
  "previous_hash": null  // First entry has no predecessor
}

Entry 2:
{
  "id": 2,
  "timestamp": "2026-05-02T15:30:45Z",
  "event_type": "deploy.started",
  "hash": "sha256:def456...",
  "previous_hash": "sha256:abc123..."  // References Entry 1's hash
}

Entry 3:
{
  "id": 3,
  "timestamp": "2026-05-02T16:00:00Z",
  "event_type": "deploy.completed",
  "hash": "sha256:ghi789...",
  "previous_hash": "sha256:def456..."  // References Entry 2's hash
}
```

### 2.2 Tamper Detection via Hash Chain

**Scenario:** Attacker modifies Entry 1

```
Original Entry 1:
{
  "hash": "sha256:abc123...",
  "event_type": "release.created",
  ...
}

Attacker changes "release.created" → "release.deleted"
New hash = "sha256:zzz999..."

But Entry 2 still has:
{
  "previous_hash": "sha256:abc123..."  // ← Mismatch!
  ...
}

Verification detects:
  Calculate(Entry 1 content) = "sha256:zzz999..."
  Expected from Entry 2 = "sha256:abc123..."
  ✗ MISMATCH → Tamper detected!
```

### 2.3 Hash Chain Math

**Hash of entry i depends on:**
- Content of entry i
- Hash of entry i-1
- (Indirectly) content of entry i-1, entry i-2, ... entry 1

**To successfully modify entry 1:**
1. Modify entry 1 content
2. Recalculate entry 1's hash
3. Update entry 2's `previous_hash` field
4. Recalculate entry 2's hash
5. Update entry 3's `previous_hash` field
6. ... repeat for all N entries

**Verification detects:** If any entry is modified without updating all downstream entries

**Blockchain analogy:**
- Bitcoin: hash of block i includes hash of block i-1
- Audit log: hash of entry i includes hash of entry i-1
- Both: modification forces recalculation of entire chain downstream

**Time complexity of attack:**
- Modify 1 entry → O(N) hash recalculations
- Recompute all hashes → O(N) time
- Detect tampering → O(N) time to verify

**Defense: Append-only ledger**
- New entries always appended, never inserted/deleted
- Old entries never modified
- Verification starts from most recent entry and walks backward


**Step 2: Serialize to canonical JSON**

```
{"action":"release.approve",...,"reason":"All SDLC gates..."}
(no whitespace, sorted keys)
```

**Step 3: Generate hash**

```
document_hash = SHA-256(canonical_json)
             = "abc123def456789abc123def456789abc123def456789abc123def456789abc1"
```

**Step 4: Exchange OIDC token for ephemeral certificate**

```
OIDC Token (from GitHub Actions):
{
  "iss": "https://token.actions.githubusercontent.com",
  "sub": "repo:ruralpeds/.github:environment:production",
  "aud": "sigstore",
  "iat": 1714754400,
  "exp": 1714754700,  // 5 min validity
  "github_workflows_ref": "refs/heads/main",
  "github_workflows_sha": "abc123...",
  "github_run_id": "12345678",
  "ref_protected": "true"
}

GitHub signs token with private key (JWKS rotation)
↓
Cosign sends token to Fulcio CA
↓
Fulcio verifies:
  ├─ Signature valid (GitHub public key from JWKS)
  ├─ Not expired
  ├─ Intended audience is "sigstore"
  └─ Issuer is GitHub (https://token.actions.githubusercontent.com)

Fulcio issues certificate:
{
  "subject": "CN=sigstore-signer",
  "extensions": {
    "github_workflows_ref": "refs/heads/main",
    "github_workflows_sha": "abc123...",
    "github_run_id": "12345678"
  },
  "validity": {
    "not_before": "2026-05-02T16:00:00Z",
    "not_after": "2026-05-02T16:05:00Z"  // 5 min
  },
  "signature_algorithm": "ECDSA-SHA256",
  "issuer": "CN=Fulcio Root CA"
}
```

**Step 5: Sign document hash with ECDSA**

```
private_key = Fulcio-issued key (in cosign memory)
document_hash = "abc123def456..."
signature = ECDSA-sign(document_hash, private_key)
          = (r, s)  // Two 256-bit components
          = "MEYCIQDx...base64...zw==" (when base64-encoded)

Private key immediately discarded after signing
```

**Step 6: Create signed envelope**

```json
{
  "version": "1.0",
  "envelope_type": "approval",
  "timestamp": "2026-05-02T16:00:00Z",
  
  "document": {
    "action": "release.approve",
    "release_version": "v2.3.1",
    ... (full approval document)
  },
  
  "signature": {
    "bytes": "MEYCIQDx...base64...zw==",
    "algorithm": "ECDSA-SHA256",
    "certificate": "-----BEGIN CERTIFICATE-----\nMIIC...-----END CERTIFICATE-----",
    "certificate_chain": [
      "-----BEGIN CERTIFICATE-----\n...Fulcio Intermediate CA...",
      "-----BEGIN CERTIFICATE-----\n...Fulcio Root CA..."
    ]
  },
  
  "document_hash": "sha256:abc123def456...",
  "previous_envelope_hash": "sha256:def456ghi789...",
  "envelope_hash": "sha256:jkl012mno345...",
  
  "rekor": {
    "uuid": "24296fb24b8ad77a72ef06bd8e53ae3eccd51d2c5ff60219e0f3d9088f3ea2f9",
    "entry_url": "https://rekor.sigstore.dev/api/v1/log/entries/24296fb24b8ad77a72ef06bd8e53ae3eccd51d2c5ff60219e0f3d9088f3ea2f9"
  }
}
```

### 3.2 Multi-Step Verification

**Verification steps (in order):**

```
1. Parse & validate structure
   ├─ JSON structure valid
   ├─ Required fields present
   └─ Version supported

2. Verify document hash chain
   ├─ Recalculate document_hash from document
   ├─ Compare to envelope.document_hash
   └─ FAIL if mismatch → envelope/document tampered

3. Verify envelope hash chain
   ├─ Recalculate envelope_hash from envelope (including sig, cert)
   ├─ Compare to envelope.envelope_hash
   └─ FAIL if mismatch → envelope tampered

4. Verify signature
   ├─ Extract signature bytes
   ├─ Extract signer certificate (public key)
   ├─ Perform ECDSA verification:
   │  ├─ Input: document_hash, signature, public_key
   │  ├─ Output: valid or invalid
   │  └─ Calculation: (r, s) is valid if: r*G + hash*Q ≡ R (mod p)
   │     where Q = public key, R = point with x-coordinate r
   └─ FAIL if invalid → not signed by signer

5. Verify certificate chain
   ├─ Build chain: leaf (signer cert) → intermediate CAs → root CA
   ├─ For each cert in chain:
   │  ├─ Verify signature of cert i with public key of cert i+1
   │  ├─ Check validity dates (not_before ≤ now ≤ not_after)
   │  ├─ Check extensions (CN, OID, SANs)
   │  └─ FAIL if any check fails
   ├─ Verify root CA is trusted (in system's trusted root store)
   └─ FAIL if chain is broken

6. Verify certificate not revoked
   ├─ Query OCSP responder
   │  └─ POST to OCSP URL (from cert)
   ├─ Check revocation status
   ├─ Verify OCSP response signature
   └─ FAIL if revoked

7. Verify Rekor entry
   ├─ Query Rekor transparency log for envelope_hash
   ├─ Verify entry exists
   ├─ Verify entry content matches envelope
   ├─ Check timestamp (±5 min from envelope timestamp)
   └─ FAIL if entry missing or mismatched

8. Verify timestamp ordering
   ├─ Compare envelope.timestamp to previous_envelope.timestamp
   ├─ Ensure current > previous (monotonically increasing)
   └─ FAIL if timestamps out of order

Result: ✅ VALID & AUTHENTIC
        (or detailed error indicating failure point)
```

## Rekor Transparency Log Integration

### 4.1 What is Rekor?

**Rekor** = "record" in Spanish  
**Purpose:** Immutable, append-only transparency log for cryptographic signatures

**Why?**
- Single signature can be forged (if private key stolen)
- Signature + public cert chain can be forged (cert revoked later, attacker doesn't know)
- Rekor provides **independent verification**: "This signature was publicly logged at this exact time"

**Properties:**
- **Append-only:** Once logged, entry cannot be modified/deleted
- **Cryptographically signed:** Log entries are signed by Sigstore's private key
- **Merkle tree:** Log entries organized in a binary Merkle tree for efficient verification
- **STH (Signed Tree Head):** Root hash of Merkle tree, signed by Sigstore's private key
- **Public:** Anyone can query `https://rekor.sigstore.dev/`

### 4.2 Entry Format

**When cosign uploads signature to Rekor:**

```json
Entry payload:
{
  "kind": "hashedrekord",
  "apiVersion": "0.0.1",
  "spec": {
    "data": {
      "hash": {
        "algorithm": "sha256",
        "value": "abc123def456..."
      }
    },
    "signature": {
      "content": "MEYCIQDx...base64...",
      "publicKey": {
        "content": "-----BEGIN CERTIFICATE-----\nMIIC..."
      }
    }
  }
}

Rekor generates entry:
{
  "uuid": "24296fb24b8ad77a72ef06bd8e53ae3eccd51d2c5ff60219e0f3d9088f3ea2f9",
  "integratedTime": 1714754400,
  "logID": "c0d23d6ad406973f9559f3ba6d3c45c7e36c80d969c074e37e8180500bccf550",
  "logIndex": 123456789,
  "verification": {
    "signedEntryTimestamp": "MEUCIQDx...base64...",
    "logID": "c0d23d6ad406973f9559f3ba6d3c45c7e36c80d969c074e37e8180500bccf550"
  }
}
```

**Fields:**
- **uuid:** Unique entry identifier (content hash)
- **integratedTime:** Unix timestamp when entry logged
- **logIndex:** Position in Merkle tree (used for binary search)
- **signedEntryTimestamp:** Signature of entry by Rekor's signing key
- **logID:** Which Rekor shard (production, staging, etc.)

### 4.3 Merkle Tree Verification

**Rekor stores entries in a Merkle tree:**

```
                    Root (hash)
                   /           \
              H(node0-1)      H(node2-3)
              /        \      /        \
         H(0) H(1)  H(2) H(3) ...

Each entry is a leaf. Rekor publishes:
  - Merkle tree structure
  - Signed Tree Head (STH): signature of root hash
```

**Verification:**

```bash
# User has: envelope_hash, Rekor entry UUID

# 1. Query Rekor for entry
rekor-cli search --artifact envelope_hash

# 2. Rekor returns: entry, logIndex, signedEntryTimestamp

# 3. Verify signature of entry
#    ├─ Entry content
#    ├─ signedEntryTimestamp (signature)
#    ├─ Rekor's public key (from OIDC cert)
#    └─ ECDSA verify(content, signature, rekor_pubkey)
#       → ✅ VALID or ❌ FORGED

# 4. Optional: Verify entry is in Merkle tree
#    ├─ Calculate hash of entry
#    ├─ Use logIndex to construct path to root
#    ├─ Recalculate root hash
#    ├─ Fetch STH (Signed Tree Head) from Rekor
#    ├─ Verify STH signature (Rekor's private key)
#    └─ If recalculated root == STH root → entry in tree
```

**Why this matters:**
- **Prevents backdating:** If attacker tries to log entry with old timestamp, Merkle tree position doesn't match
- **Prevents removal:** If Rekor operator deletes entry, next STH won't include it, verification fails
- **Immutability proof:** Anyone can independently verify using Rekor's public key

## Verification & Tamper Detection

### 6.1 Verification Workflow

**Automated verification runs daily:**

```
audit-verify.yml (Daily at 20:00 UTC)
  ↓
[Collect recent entries: past 24 hours]
  ├─ Query cloud audit logs (CloudTrail, Azure, etc.)
  ├─ Filter by timestamp
  └─ Download last 50-1000 entries
  
  ↓
[Hash chain validation]
  ├─ For each entry:
  │  ├─ Recalculate hash from entry content
  │  ├─ Compare to stored hash
  │  ├─ Verify: previous_hash == actual_previous_entry.hash
  │  └─ If mismatch → add to tamper_detections
  
  ├─ Build graph: entry → previous_entry
  ├─ Detect breaks: entry i's previous_hash ≠ entry(i-1)'s hash
  └─ Report: N tampering detections (0 = good)
  
  ↓
[Signature verification (sampled)]
  ├─ For 10% random sample of signed entries:
  │  ├─ Extract signature + cert
  │  ├─ cosign verify-blob verification
  │  ├─ Verify cert chain
  │  └─ If invalid → add to forgery_detections
  
  └─ Report: N forgery detections (0 = good)
  
  ↓
[Rekor validation]
  ├─ For all signed entries:
  │  ├─ Query Rekor for entry_hash
  │  ├─ Verify: entry found
  │  ├─ Verify: timestamp within ±5 min
  │  └─ If not found → add to missing_entries
  
  └─ Report: N missing entries (0 = good)
  
  ↓
[Generate report]
  ├─ Total entries verified: N
  ├─ Hash chain: ✅ VALID or ❌ BROKEN
  ├─ Signatures: ✅ VALID or ❌ FORGED
  ├─ Rekor: ✅ COMPLETE or ❌ GAPS
  ├─ Detections: [tamper_detections, forgery_detections, missing_entries]
  └─ If any detection → create GitHub issue, alert security team
```

### 6.2 Tamper Detection Examples

**Scenario 1: Entry modified**

```
Original:
Entry 42:
{
  "hash": "sha256:abc123...",
  "event_type": "release.created",
  "result": "success",
  "previous_hash": "sha256:def456..."
}

Entry 43:
{
  "hash": "sha256:ghi789...",
  "previous_hash": "sha256:abc123...",
  ...
}

Attack: Modify Entry 42's result from "success" to "failure"
New Entry 42:
{
  "hash": "sha256:abc123...",  // ← unchanged by attacker
  "event_type": "release.created",
  "result": "failure",  // ← MODIFIED
  "previous_hash": "sha256:def456..."
}

Verification:
  recalc_hash = SHA-256(modified_entry_42_content)
              = "sha256:zzz999..."
  
  stored_hash = "sha256:abc123..."
  
  recalc_hash ≠ stored_hash → ✗ TAMPER DETECTED
```

**Scenario 2: Hash chain broken**

```
Attacker successfully modifies Entry 42 and recalculates its hash to "sha256:xxx888..."

But they forgot to update Entry 43's previous_hash field
Entry 43 still has:
{
  "previous_hash": "sha256:abc123...",  // ← Old hash
  ...
}

Verification:
  For Entry 43:
    expected_previous_hash = entry_43.previous_hash = "sha256:abc123..."
    actual_previous_hash = SHA-256(entry_42_content) = "sha256:xxx888..."
    
    expected ≠ actual → ✗ CHAIN BREAK DETECTED
```

**Scenario 3: Rekor entry missing**

```
Attacker deletes entry from Rekor (if they had Rekor admin access)
```

## Storage & Retention

### 7.1 Multi-Tier Storage

**Primary: Cloud Audit Logs**

```
AWS CloudTrail (if using AWS):
  ├─ S3 bucket: audit-logs-prod (immutable, versioned)
  ├─ Object Lock enabled:
  │  ├─ Mode: COMPLIANCE (cannot delete, even by root)
  │  ├─ Retention: 7 years
  │  └─ Legal hold: Can extend indefinitely
  ├─ Encryption: KMS with separate CMK
  ├─ Access: IAM role limited to read-only for auditors
  ├─ MFA delete: Required for any deletion attempt
  └─ Versioning: Enabled (immutable history)

Logging of access:
  └─ All S3 API calls logged to CloudTrail
     (accessing audit logs is itself logged)
```

**Secondary: Rekor Transparency Log**

```
Rekor (Public, Sigstore-hosted):
  ├─ Endpoint: https://rekor.sigstore.dev/
  ├─ Signed entries: Each entry signed by Rekor's key
  ├─ Merkle tree: Cryptographic proof of entry inclusion
  ├─ STH (Signed Tree Head):
  │  ├─ Root hash of tree
  │  ├─ Signed by Rekor private key
  │  ├─ Published at each update
  │  └─ Anyone can verify against Rekor public key
  └─ Publicly verifiable: rekor-cli search, verification tools
```

**Tertiary: Repository Commits**

```
.git/logs/ (Git reflog):
  ├─ audit-log/ledger.jsonl
  │  ├─ Appended with each event
  │  ├─ History: git log -- audit-log/ledger.jsonl
  │  └─ Commit history: immutable once pushed
  ├─ Git tags: sig-v2.3.1 → GPG-signed commit
  └─ Branches: main has reflog history
  
git log --oneline --all:
  ├─ Shows all commits (including merged branches)
  ├─ Commit hash deterministic (content-based)
  ├─ Rewriting history requires git filter-repo (destructive)
  └─ Protected main branch: no force-push allowed
```

### 7.2 Retention Policy

**Compliance requirements:**
- HIPAA: 6 years minimum (we do 7)
- 21 CFR Part 11: "System must provide a means to...retain records"
- IEC 62304: Appendix F requires "audit trail"

**Implementation:**

```
Timeline:
Day 0: Event occurs
  ↓
Day 0: Logged to all three tiers
  ├─ CloudTrail (real-time)
  ├─ Rekor (within 30 seconds)
  └─ Git commit (within 5 minutes)

Day 1-90: Hot storage (frequently accessed)
  ├─ CloudTrail: Standard S3 storage class
  ├─ Rekor: In-memory Merkle tree
  └─ Git: Local repository

Day 91-365: Warm storage (occasional access)
  ├─ CloudTrail: S3 Glacier Flexible Retrieval (4-12 hour thaw)
  └─ Rekor: Still fully queryable

Year 1-7: Cold storage (rare access, long-term compliance)
  ├─ CloudTrail: S3 Glacier Deep Archive (12-48 hour thaw)
  ├─ Git: Still cloned, backed up
  └─ Rekor: Still queryable

Year 7: Deletion (or longer if legal hold)
  ├─ CloudTrail Object Lock expires
  ├─ S3 lifecycle rule deletes archive
  ├─ (Rekor is indefinite public record)
  └─ (Git history retained indefinitely by default)
```

## Event Lifecycle

### 8.1 Complete Event Journey

**From trigger to verification:**

```
Time: 2026-05-02 15:30:45 UTC

[Release Gate 5 Passed]
  GitHub Actions workflow: 03-release-and-deploy.yml
  │
  └─ Step: Record release event
     │
     ├─ Create audit entry JSON
     │  {
     │    "timestamp": "2026-05-02T15:30:45Z",
     │    "event_type": "release.created",
     │    "actor": "system/ci",
     │    "resource": "app@v2.3.1",
     │    "result": "success"
     │  }
     │
     ├─ Generate hash
     │  hash = SHA-256(canonical_json)
     │       = "abc123def456..."
     │
     ├─ Calculate envelope hash (with previous_hash)
     │  envelope_hash = SHA-256({...content..., "previous_hash": "def456ghi789..."})
     │               = "jkl012mno345..."
     │
     └─ Create signed envelope
        {
          "document": {...event...},
          "signature": {...cosign signature...},
          "document_hash": "sha256:abc123...",
          "previous_envelope_hash": "sha256:def456...",
          "envelope_hash": "sha256:jkl012...",
          "rekor": {
            "uuid": "24296fb24b8ad77...",
            "entry_url": "https://rekor.sigstore.dev/..."
          }
        }

T+30s: Envelope uploaded to Rekor
   │
   └─ POST /entries → Rekor
      ├─ Rekor stores envelope
      ├─ Assigns entry ID (UUID)
      ├─ Includes in Merkle tree
      └─ Returns: entry_uuid, logIndex

T+1m: Envelope committed to Git
   │
   ├─ audit-log/ledger.jsonl appended
   ├─ Git commit created: "audit: release.created v2.3.1"
   ├─ Commit hash: abc123def456...
   └─ Pushed to main branch

T+30min: Compliance dashboard updated
   │
   └─ audit-dashboard-sweep.yml runs every 6 hours
      ├─ Collects recent entries
      ├─ Updates dashboard JSON
      └─ Refreshes visualization

T+24h: Daily verification
   │
   └─ audit-verify.yml runs daily at 20:00 UTC
      ├─ Verifies all entries from past 24h
      ├─ Validates hash chains
      ├─ Samples signature verification
      ├─ Checks Rekor entries
      └─ Reports: ✅ VERIFIED (0 detections)

T+90d: Archive to cold storage
   │
   └─ S3 lifecycle rule triggers
      ├─ Move from standard → Glacier Flexible Retrieval
      ├─ Still accessible for audit (thaw time: 4-12h)
      └─ Cost reduction: ~90% savings

T+7yr: Retention expires
   │
   └─ Object Lock expires
      ├─ Can delete (if desired)
      ├─ OR keep indefinitely (many do)
      └─ Rekor copy remains public forever
```

## Regulatory Compliance Mechanisms

### 9.1 HIPAA §164.312(b) — Audit Controls

**Requirement:** "Implement hardware, software, and procedural mechanisms that record and examine activity in information systems containing or using electronic protected health information."

**Implementation:**

| Requirement | Mechanism |
|-------------|-----------|
| Record activities | Audit log entry created for every regulatory event |
| Record WHO | Actor field identifies system/user |
| Record WHAT | Event type and resource describe action |
| Record WHEN | ISO 8601 timestamp (UTC) |
| Record result | Success/failure/warning outcome |
| Prevent modification | Hash chain + signature + Rekor |
| Retention ≥6 years | S3 Object Lock, Glacier archive |
| Accessible for review | Audit dashboard, CloudTrail, Rekor queries |
| Access logging | All audit log access logged to CloudTrail |

### 9.2 21 CFR Part 11 §11.70 — Electronic Signatures

**Requirement:** "When an electronic signature is used, the system shall implement..." control measures to ensure signature authenticity

**Implementation:**

| Requirement | Mechanism |
|-------------|-----------|
| Identity verification | OIDC token issued by GitHub (verified by Fulcio) |
| Signature cannot be repudiated | ECDSA signature mathematically prevents denial |
| Signature prevents alteration | Hash of document; modification changes signature invalid |
| Audit trail | Rekor transparency log + Git history + CloudTrail |
| System prevents forgery | Private key never on CI runner; ephemeral cert from Fulcio |
| Date/time embedded | ISO 8601 timestamp in envelope |

### 9.3 IEC 62304 §5.7.3 — Software Release

**Requirement:** "The organization shall...define and document all aspects of release and delivery that affect...traceability."

**Implementation:**

| Aspect | Implementation |
|--------|-----------------|
| Release record | Audit entry captures release event, version, artifacts |
| Approved by | Signature envelope shows approver (signer cert) |
| Traceability | Links to requirements (via RTM), code (commit), tests (gate 4) |
| Verification | SLSA provenance, SBOM, signatures |
| Change history | Git log shows all commits leading to release |
| Proof of approval | Electronic signature (non-repudiable) |
| Immutable record | Hash chain prevents tampering |

## Rust Repository Tracking System

### 10.1 Automatic Repository Discovery

**The `build-status-sweep.yml` workflow discovers and tracks all Rust repos:**

**Workflow:** `.github/workflows/build-status-sweep.yml`
**Frequency:** Every 30 minutes (scheduled) or on-demand (workflow_dispatch)
**Owner:** Timothy Hartzog (@timothyhartzog)

**Discovery logic:**

```bash
# Step: Build sweep matrix
for_each_language in ["Rust", "Julia"]:
  repos = gh repo list ruralpeds --language ${language} --limit 100
  
  # Filter: Only repos with .gap-analysis/GAP_ANALYSIS.md
  for repo in repos:
    if [ -f "${repo}/.gap-analysis/GAP_ANALYSIS.md" ]:
      gap_repos.append(repo)
      log "✓ $repo has .gap-analysis/"
    else:
      log "- $repo no .gap-analysis/ — skipping"

gap_repos.append("ruralpeds/.github")

# Output: matrix for parallel processing
output: {
  "matrix": gap_repos,
  "readme_repos": gap_repos
}
```
